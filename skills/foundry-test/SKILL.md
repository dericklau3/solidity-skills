# 编写并验证 Foundry 测试

## 遵守本技能

执行时遵守本技能适用的范围、执行规则、验证要求和输出约定。不静默跳过必需步骤，不用建议代替已授权的实现。用户明确指令及更高优先级指令优先。必需步骤无法完成时，说明具体限制、继续独立工作，不宣称该步骤已经完成。

## 执行范围

调用本技能，或要求检查、改进测试，默认意味着识别缺口、直接补好相关测试并运行 `forge test`。完成实际工作，不停留在发现、建议或测试计划。用户明确要求仅解释、仅运行现有测试或保持只读时，遵循用户指定的范围。

用户指定文件或行为时按其范围执行，否则使用项目配置的源码和测试目录。保留无关改动与现有测试组织方式。只有用户授权的工作包含修复时，才可修改生产行为；单纯补测试不代表允许改变协议。

某项预期行为无法确定时，不新增依赖该未确定业务假设的断言，也不据此删除或削弱既有测试；报告疑点并继续独立测试。只有无法从项目获取、且实质影响正确性的信息才需要询问；沿用用户已经给出的授权。

## 目标网络 Fork 与 setUp

业务合约测试默认必须 Fork 项目目标网络并固定区块，包括该业务合约的 Unit、Fuzz 和 Invariant 测试。测试层级不决定是否 Fork。纯数学、独立工具库等不依赖链状态的测试可以在本地运行，但不能替代业务流程的 Fork 验证。用户明确指定其他测试环境时遵循其要求并说明覆盖边界。

编写测试前读取当前项目的 `test/Wallet.t.sol` 或等价测试、`ContractCollection`、`BaseDeployScript` 和 `foundry.toml`。从用户指定目标、项目部署配置及 RPC 别名确定网络；确认这些来源一致，不照搬模板中的 `base` 或区块号。优先沿用项目已有的适用固定区块；新选区块应确认目标合约和依赖在该区块已存在，记录网络、chain ID、区块号及选择理由。目标网络无法确定时询问，不猜测。

沿用 foundry-starter 的测试类结构：继承 `ContractCollection, Test`，或复用已封装同等流程的项目测试基类。`setUp()` 保持以下顺序：

1. 使用 `vm.createSelectFork(项目RPC别名, 固定区块号)` 选择 Fork，在读取链配置或部署之前核对 `block.chainid` 与目标一致。
2. 使用项目测试部署账户进入 `vm.startBroadcast(account)` 上下文，不读取真实私钥来完成测试初始化。
3. 通过 `cfg = _getConfig()` 获取该链配置，检查必需地址和参数。
4. 使用 `deployXxx(cfg...)` 等现有 `ContractCollection` helper 部署并初始化被测合约，保留真实参数顺序和执行身份，不在测试中另写一套代理部署或初始化逻辑。
5. 调用 `vm.stopBroadcast()`，随后检查 owner、角色及关键初始化结果，保证各测试从预期状态开始。

这里的广播上下文仅用于本地 Fork 测试中的部署身份模拟，不执行链上广播。复用部署 helper 时检查文件写入等副作用；若 helper 会保存注册表，利用项目已有的可覆盖文件名等机制隔离测试输出，不覆盖真实部署地址记录。

测试数据准备可以使用必要的 `deal`、prank 或恶意 mock，但不能替代已要求的目标链 Fork、真实外部依赖或被测部署路径。项目缺少部署 helper 时，先按实际部署流程建立可复用路径，不凭空套用 Wallet 的业务配置。

缺少 RPC、环境变量或历史区块状态时，明确报告 Fork 验证受阻；不得静默切换其他网络、改成 mock-only、提前返回或跳过测试后宣称通过。继续可独立运行的检查，并区分本地检查通过与 Fork 尚未验证。

## 第三方协议必须使用真实部署

测试涉及任何实际集成的第三方链上协议时，必须调用目标网络固定区块 Fork 上的真实部署，包括但不限于 Uniswap、PancakeSwap、Aave；不限于 DEX 或借贷协议。这适用于所有测试层级；不能因为标为 Unit、Fuzz 或 Invariant 就用自建 mock、stub 或本地重新部署的仿制协议替代。仅创建 Fork、实际仍调用 mock，不算真实协议测试。

- 从项目配置、实际部署记录或协议官方部署资料确认网络、版本及地址，并在选定区块检查代码和关键配置。不得凭记忆填地址或混用不同链、不同版本的组件。
- DEX 使用实际集成的 Router、Factory、Pool/Pair、PositionManager 等组件，通过真实入口完成相关交易、流动性或回调路径。业务需要新池时，可通过 Fork 上的真实 Factory/管理器创建；不得自行写一个简化池来替代协议。
- Aave 使用实际市场的 Pool、AddressesProvider 及相关真实储备、aToken、债务 token 和预言机配置；按被测场景通过真实协议操作形成存款、借款、还款、提款或清算状态。不手工铸造替身 aToken，也不直接改余额或债务槽来伪造协议头寸。
- 禁止使用 `vm.mockCall` 等方式伪造这些协议的返回值，或通过 `vm.etch` 替换其代码。不得直接修改池储备、价格、指数或头寸存储来绕过真实操作。需要某种状态时，通过真实入口或选择有据可查的历史区块构造。
- 可为测试账户准备基础资产、设置调用身份，或部署攻击者/回调接收合约；这些辅助行为不能替代真实协议、伪造集成结果或破坏协议会计。资金准备方式及其局限应在测试中说明。
- 地址、RPC、历史状态、流动性或市场配置不可用时，报告具体阻塞并保留未完成范围，不降级为 mock 后宣称该集成已通过。

## 发现并实现

1. 阅读 `foundry.toml`、相关合约、现有测试、fixture 和 mock。README、初始化/部署脚本、实际安装依赖影响行为时再读取它们。解析自定义目录和 remapping，不假定一定使用 `src/`、`test/` 或记忆中的库 API。
2. 从入口、资产、角色、会计单位、权限和状态转换推导预期行为。优先覆盖资金安全、会计/偿付能力、权限、核心状态转换、数学/取整和边界。现有测试仅是意图证据，不能单独充当业务规范。
3. 按下表选择能够证明缺失保证的最轻测试层。复用项目命名、fixture、helper 和断言风格，不替换整套测试，也不整批复制依赖库测试。
4. 声称覆盖真实用户流程时，使用真实初始化路径和 public 入口。只有不会绕过被测行为且符合上方真实协议要求时才使用辅助 mock 或 shortcut；实际集成的第三方协议不得被替代。按需覆盖必需 hook、initializer 顺序、callback 和升级集成。Fork 按上方目标网络与固定区块规则执行，环境假设写在相关断言旁。
5. 涉及部署或升级流程时，将测试路径与实际发布脚本逐项核对：调用对象、调用顺序、初始化参数、执行身份和升级范围。复用 helper 前确认其没有额外升级组件或绕过真实初始化；独立组件测试与发布流程测试分开。脚本不可用或路径不一致时，明确证据缺口，不把辅助流程测试通过描述为真实发布流程已验证。本地或 Fork 通过不代表已广播或已验证当前链上状态。
6. 编写测试、运行相关命令、诊断失败并完成已授权工作。不生成独立的 `test/docs` 文件。

| 测试层 | 要证明的内容 |
| --- | --- |
| Unit | 单次操作的结果、状态、资产流、event、边界、revert 或权限。 |
| 集成 / 真实流程 | 多合约交互、部署配置，或从实际 public 入口到达的操作序列。 |
| Fuzz | 有意义参数范围内的属性，例如守恒、单调性、取整上限或非法输入拒绝。 |
| Stateful invariant | 多样化用户/操作员动作序列中必须保持的协议承诺。 |

避免机械追求覆盖率。Invariant 必须从当前协议推导；增加状态序列探索前，先覆盖重要的单次操作行为。

## 测试质量

每个新增或实质修改的 `test...()` 或 invariant 函数，在左花括号后立即用一两行注释说明目的。写清行为或防止的失败；Fuzz 说明属性与输入范围，Invariant 说明跨调用序列的承诺。

- 按需断言有意义的结果：余额、份额/债务/奖励、费用、event、错误 selector、权限及其他用户状态。只有明确的取整、换算、时间或外部数学原因才能使用近似断言。
- 回归测试构造能触发失败条件的最小状态，避免意外激活另一条成功路径。按需验证关键边界、重复操作和顺序变化。
- 缺陷版本可获得时，在该版本运行回归测试，确认失败来自原始 bug，而非编译、初始化或环境错误；再用相同的行为断言验证修复版本通过。隔离前后对比，保留无关工作。缺陷版本或对比环境不可用时，明确说明未验证修复前失败；仅修复版本测试通过，不足以证明能够捕获原始 bug。若实现修复不在授权范围内，保留并报告有效的失败回归测试，不修改生产代码。
- Fuzz 连续范围优先使用 `bound()`；难以用边界表达的约束才用精确的 `vm.assume()`。包含边界值，不为通过测试而过滤反例。
- Stateful invariant 仅在业务承诺成立时推导会计、偿付能力、守恒、供给、权限、状态机和经济属性。明确建模费用、损失、mint/burn 与允许的 donation。
- 使用真实 handler，按需建模多参与者，通过 `targetContract(address(handler))` 与必要的 `targetSelector()` 限定动作。让动作多样且有效，避免大多数调用只会 revert。协议状态无法还原的流量用 ghost variable 记录；handler guard 不得隐藏协议的非法状态。
- 将失败 invariant 序列缩减为真实复现。区分测试假设错误、生产行为错误和环境问题。保留有效复现，不为变绿而削弱断言、扩大 tolerance 或修改生产行为。

## 验证范围

新增或修改测试后必须运行相应测试。用户仅要求解释或静态评审时，可读取相关文件，但不自动运行构建或测试命令；仅要求运行现有测试时，不修改文件。只读要求本身不代表禁止运行已明确请求的测试。按实际请求选择范围：

| 改动 / 请求 | 必需执行 |
| --- | --- |
| 仅解释或静态评审 | 不修改文件、不自动运行测试；基于已有资料回答并说明未执行验证。 |
| 仅运行现有测试 | 执行用户指定或与问题相关的测试，不新增测试或修改实现。 |
| 单个独立测试或局部行为 | 相关 `forge test --match-path <path>` 或 `forge test --match-test <name>`；诊断失败时增加 `-vvvv`。 |
| 共享 fixture/helper、核心会计、公共行为或多合约交互 | 先运行聚焦测试，再覆盖所有受影响套件；依赖面广或无法可靠限定时运行完整 `forge test`。 |
| 全项目测试强化或明确要求全量 | 完整 `forge test`，包括项目要求且适用的 profile。 |
| 仅测试注释改动 | 运行相关测试文件，不额外新增 Fuzz/Invariant 或运行无关全量测试。 |

编辑后对修改文件运行 `forge fmt --check` 并检查 diff。完成项目要求的检查。必需检查通过后，仅因新增改动、失败或未解决疑点扩大或重复验证；输入和配置未变时复用已有有效结果。

缺少 RPC、依赖或环境变量时，继续可运行的独立检查并说明具体受阻命令。区分新失败与基线失败；局部通过不等于全量通过。

## 最终回复

按请求类型回复：实现任务简短说明补了哪些测试及实际验证结果；仅运行任务报告执行结果；解释或静态评审任务直接回答问题并说明未运行测试。仅在影响完成时说明剩余阻塞或有效的失败复现。实现任务的场景解释保留在测试注释中，不另行输出发现报告、建议清单或测试计划；用户明确要求解释或评审时，按请求提供相应分析。
