# 语义级代码裁剪

## 目标

使用这个 skill 删除不增加可观察行为的代码。这不是代码风格整理、代码压缩或普通重构，而是一次保持语义不变的裁剪：每一次删除都必须有证据证明，在所有受支持的调用方和输入下，程序行为保持一致。

优先选择可以证明行为不变的小改动，而不是看起来更简洁但证明不足的聪明重写。

## 裁剪标准

一行代码、一个分支、一个 helper、一个返回值或一个 guard，只有同时满足以下三个条件时才可以删除：

1. 它的结果已经由周围控制流、类型、状态、不变量、调用方契约或更早的校验保证。
2. 删除它不会改变外部可观察行为，包括返回值、错误、日志、事件、数据库写入、网络调用、storage layout、对时序敏感的副作用、metrics 或公开 API 形态。
3. 这个证明可以从代码证据解释，而不是基于个人审美、命名，或“当前测试没有覆盖这个场景”。

如果证明依赖仓库、配置、运行环境或公开契约之外的假设，除非用户确认这些假设，否则只把它作为建议，不要直接修改。

## 需要收集的证据

编辑前，阅读足够上下文来证明冗余：

- 调用图：谁能到达这段代码，带着什么参数，经过了哪条校验路径。
- 数据流：这个值在哪里赋值、转换、被观察、返回、持久化，或传给有副作用的代码。
- 控制流：前置分支、异常、guard、模式匹配或状态机转换是否已经让代码不可达或重复。
- 契约和接口：签名、override、序列化格式、schema、ABI/API 兼容性或生成客户端是否依赖当前形态。
- 副作用：代码是否触及 IO、存储、日志、telemetry、锁、缓存、随机数、时间、外部调用、callback 或生命周期 hook。
- 测试和运行证据：哪些聚焦测试、build、类型检查、snapshot 或 trace 能确认裁剪后的行为。

当项目使用特定领域框架时，要尊重框架里的隐藏契约。例如 React hook 规则、数据库 migration 顺序、Solidity upgradeable storage layout、协议 event 形态、公开 SDK API、CLI 输出和生成代码边界。

## 通常可以删除什么

| 候选项 | 只有在以下情况才删除 |
|---|---|
| 冗余赋值 | 所有到达路径已经让变量拥有相同值，并且没有观察者依赖这次写入本身。 |
| 未使用返回值 | 没有调用方消费它，它不是 interface / override / protocol 所要求的一部分，并且删除它不会改变公开 API 形态。 |
| 重复 guard | 所有到达路径都已经强制检查过同一条件，并且错误语义等价，也不存在有意保留的不同诊断信息。 |
| 透传临时变量 | 变量只赋值一次、读取一次，没有调试或文档价值，并且内联不会遮蔽领域含义。 |
| 死分支 | 根据当前前置条件、状态机规则、类型约束或穷尽匹配，该分支不可达，并且它不是为外部输入或未来状态有意保留的防御代码。 |
| 薄 wrapper | helper 只是给一个调用改名，没有增加不变量、边界、日志、重试、授权、归一化或领域词汇。 |
| 冗余转换 | 转换不会改变表示、精度、所有权、编码或校验状态。 |
| 重复计算 | 复用或删除不会影响求值顺序、溢出 / 舍入、惰性执行、memoization 或副作用。 |

## 什么必须保留

不要因为代码看起来吵就删除它。以下职责需要保留：

- 公开契约：API/ABI 形态、override 兼容性、序列化输出、CLI 输出、event / log 格式、错误类型或 revert / error selector。
- 安全边界：不可信输入校验、权限、资产流动、认证 / session 检查、重入 / 锁、并发协调或能力隔离。
- 运维边界：日志、metrics、审计轨迹、tracing、清理、rollback、重试、限流、缓存失效、migration 步骤或 feature flag。
- 领域含义：承载业务语言、合规规则、会计分类、协议状态或团队约定的命名和 wrapper。
- 有真实契约的未来兼容：面向文档化配置范围、版本偏差、外部集成、升级路径或数据迁移的 guard。
- 生成代码或框架拥有的代码：必须匹配 schema、代码生成器、生命周期 hook、反射系统或框架约定的代码。

如果保留代码是正确的，但它看起来确实容易被误删，可以只在不变量不明显且仓库风格允许时，补一条很窄的说明注释。

## 工作流

1. 识别疑似 no-op，并分类为赋值、分支、guard、临时变量、helper、返回值、转换或重复计算。
2. 引用相关调用路径、不变量、类型规则、状态转换、接口契约或副作用分析，证明它为什么不会影响行为。
3. 检查兼容性边界：公开 API、ABI、storage / schema layout、event / log、错误行为、生成客户端、migration 和测试。
4. 应用最小删除或简化，保持行为不变。不要顺手重写附近代码，除非裁剪本身需要。
5. 先运行最窄但有意义的验证；当触达代码是共享逻辑或外部可见行为时，再扩大验证。
6. 报告删除了什么、为什么安全、哪些内容有意保留，以及哪些验证通过或失败。

## 风险等级

- 可以直接编辑：私有实现细节、无副作用、证明局部且完整，并且测试或类型检查覆盖受影响行为。
- 只有强验证时才编辑：共享 helper、通过间接调用暴露的公开行为、框架生命周期代码、并发敏感路径、数值 / 会计逻辑或序列化边界。
- 只建议不直接改：公开 API/ABI 变化、storage / schema layout 变化、删除 migration、删除安全 guard、删除审计 / 日志、兼容性行为，或依赖未文档化假设的变化。

如果有疑问，保留代码并解释不确定性。正确地不删除，比整洁地引入回归更好。

## 领域注意事项

对于 Solidity 和 Foundry 项目，除非用户明确要求更大的兼容性改动，否则保留 external / public 函数签名、event 形态、custom error selector、storage 变量顺序、initializer 参数、modifier、访问控制、upgradeable storage layout 和 revert 行为。对于外部输入、资产流动、oracle / pair 假设、权限检查、callback 和重入边界，只有在所有可达入口都证明不变量成立时才删除相关 guard。优先使用 `forge fmt --check`、`forge build` 和受影响行为的聚焦 `forge test` 验证。

对于 TypeScript、JavaScript、Go、Python 等应用代码，要特别小心 reflection、serialization、decorator、dynamic import、框架生命周期函数、dependency injection、生成类型、公开 export，以及可能被外部消费的 logging / telemetry。

## 输出约定

对每个非平凡裁剪改动，说明：

- 删除内容：文件 / 函数，以及冗余类型。
- 证明：让它冗余的不变量或调用方契约。
- 边界检查：已考虑的 API、副作用、兼容性或框架边界。
- 验证：实际运行的检查及其结果。
- 延后项：因为证明不完整或风险过高而保留的可疑代码。

最终回答保持简洁，但对行为敏感的删除不要省略证明。
